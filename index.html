技术栈

Bootstrap 自研低代码平台 Spring Boot MySQL Redis Kafka Dify

千万级数据查询性能优化 14s → 1s左右

问题背景

千万级表因 UUID 主键、字符串时间、大量 NULL 值、触发器拖累、循环入库、大字段关联及多字段 OR 模糊匹配等问题，导致查询耗时 14 秒、连接池频繁耗尽。

解决思路

  • 主键优化：UUID 主键改为自增 INT，UUID 降级为普通唯一索引，消除页分裂
  • 时间字段优化：新增 DATETIME 虚拟列替代字符串时间，建立索引，使时间范围查询走索引
  • NULL 值优化：将 data_source 和 status 的 NULL 改为默认值并设为 NOT NULL，提升索引选择性
  • 触发器异步化：删除原触发器，通过自研数据抽取平台推送至 FTP，供下游消费，解除入库同步阻塞
  • 批量入库：循环单条 INSERT 改为 JDBC batch 批量提交（500 条/批）
  • 模糊查询优化：界面改为下拉选择指定字段匹配，避免多字段 OR 模糊查询
  • 异步加载大字段：列表不加载大字段，详情按需异步加载
  • 分层冗余表：维护近 3/7/30 天冗余表，按时间范围路由到小表，减少扫描量

优化效果

慢查询耗时从平均 14 s → 降至 1 s左右

高并发标签命中校验 5-10s → 1s左右

问题背景

对外接口需校验请求数据是否命中多个标签，原串行查询数据库平均响应 10 秒左右，高并发下系统响应超时，频繁出现服务不可用。

解决思路

  • 前置过滤：无效请求直接拦截，减少无效穿透
  • 并行化：串行改并行，耗时从累加变为最大单次
  • Redis 缓存：缓存命中结果，降低数据库访问
  • 布隆过滤器：快速判断不存在的主键，避免缓存穿透
  • 异步解耦：线程池异步刷日志，接口内只生产和响应
  • 限流熔断：保障系统不被冲垮

优化效果

5-10 s → 降至 1 s左右

Kafka 异步解耦优化 11min → 30s左右

问题背景

每批数据量达 1000-3000 条，同步循环执行入库、短信、企业微信消息、语音平台推送，单条处理约 450ms，总耗时达 11-22 分钟。

解决思路

  • 引入 Kafka 实现拉取与消费分离，定时任务仅负责分页拉取 + 发送消息
  • 短信、企业微信、语音平台拆分为独立消费者组，实现故障隔离和并发控制
  • 消费端实现自动重试（指数退避，最多 3 次）+ 死信表人工补偿
  • 新增通知记录表，全链路可追溯

优化效果

  • 定时任务执行时间：11 min → 降至 30 s左右
  • 通知发送成功率：91% → 98%（自动重试）

老系统智能化升级 → 问答助手

问题背景

老系统需新增智能能力，支持用户通过自然语言生成人物行为画像报告或查询表信息。

解决思路

  • 基于 Dify 工作流编排：LLM 意图识别 → Switch 分支路由 → 画像生成 / 查表查询 / 兜底回复
  • 将 Dify Web App 通过 iframe 嵌入老系统，零侵入集成
  • 画像生成：查询老系统行为数据 → LLM 生成报告
  • 自助查询：配置化白名单 + 参数化查询，敏感字段自动脱敏

效果

  • 自然语言交互，学习成本降低 80%
  • 开发周期缩短 70%，老系统核心流程零改动
